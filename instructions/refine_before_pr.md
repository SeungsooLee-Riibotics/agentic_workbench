# Refine Before PR

이 문서는 사용자가 **내 PR 생성 직전에** 변경 사항을 한 번 더 정리해 달라고 요청했을 때 따르는 작성자 측 작업 기준이다.
목표는 diff를 더 작고 명확하게 만들고, 리뷰어가 설계 의도와 검증 근거를 빠르게 이해할 수 있게 만드는 것이다.

이 문서는 다른 사람 PR을 리뷰하는 문서가 아니다. 리뷰어 입장 문서 충분성 판정은 `pr_review_intake_gate.md`를 사용한다.

## 언제 사용하는가

아래와 같은 요청이면 이 문서를 따른다.

- "PR 올리기 전에 한 번 정리해줘"
- "불필요한 코드 있는지 봐줘"
- "비효율적인 구현이 없는지 점검해줘"
- "설계/구현 설명 문서나 PR 설명이 괜찮은지 확인해줘"

## 핵심 원칙

1. PR 전 정리는 미관 개선이 아니라 리뷰 비용과 리스크를 줄이기 위한 작업이어야 한다.
2. 현재 diff와 직접 관련된 부분만 손본다. unrelated refactor는 하지 않는다.
3. 코드를 추가하기 전에 먼저 삭제할 수 있는 불필요한 코드를 찾는다.
4. 의도가 불명확한데 설명 문서가 필요한 경우, 추측해서 채우지 말고 작업자 확인이 필요하다고 명시한다.
5. "문제 없어 보임" 같은 인상 비평 대신, 실제 근거와 확인 결과를 남긴다.

## 완료 기준

아래 조건을 만족해야 PR 준비가 된 것으로 본다.

- 변경 범위 안에 남아 있는 명백한 dead code, 중복 코드, 불필요한 임시 코드가 없다.
- 변경 범위 안에 남아 있는 불필요한 파일, 실수로 포함된 산출물, 더 이상 쓰이지 않는 보조 파일이 없다.
- 바뀐 동작의 설계 의도와 구현 이유를 리뷰어가 문서 또는 PR 설명에서 이해할 수 있다.
- 필요한 테스트, 포맷팅, 빌드 또는 수동 검증 결과가 남아 있다.
- 남는 리스크, 비대상 범위, 추가 확인이 필요한 설계 판단이 숨겨져 있지 않다.

## 작업 순서

### 1. 변경 범위 먼저 고정

- 현재 PR 후보 diff를 보고 수정 파일을 역할별로 분류한다: 로직, 테스트, 설정, 문서, 포맷팅.
- root repo인지 submodule repo인지 먼저 확인하고, 해당 repo 기준으로만 검토한다.
- 새로 추가되었거나 삭제 예정인 파일이 실제로 필요한지 먼저 확인한다.
- 현재 요청과 무관한 변경이 섞여 있으면 정리 대상에서 분리할지 사용자에게 확인하거나, 최소한 최종 보고에 명시한다.

### 2. 구현 정리

현재 diff 안에서 아래 항목을 우선 점검한다.

- 더 이상 사용하지 않는 함수, 변수, import, include, helper, TODO, debug log
- 더 이상 참조되지 않는 문서, 설정 조각, generated file, 임시 스크립트, 복사본 파일
- 임시 우회 코드가 남아 있는지 여부
- 같은 의미의 로직이 두 군데 이상 중복되는지 여부
- 단일 사용처인데 과한 추상화, wrapper, indirection을 추가했는지 여부
- naming, interface, ownership, lifetime, error handling이 변경 목적에 비해 과도하게 복잡해졌는지 여부
- 테스트가 있는데 실제 변경 의도나 회귀 위험을 제대로 검증하는지 여부

정리 원칙:

- 삭제로 해결되면 삭제를 우선한다.
- 단순화가 명확할 때만 구현을 줄인다.
- 파일 단위로 불필요함이 명확하면 PR 전에 제거한다.
- 설계 방향 자체를 바꾸는 리팩터링이 필요하면 임의로 밀어 넣지 말고 리스크로 보고한다.

### 3. 비효율 점검

성능 최적화가 목적이 아니더라도, 이번 변경이 아래와 같은 비효율을 만들었는지는 확인한다.

- 불필요한 반복 계산
- 중복된 I/O 또는 직렬화
- 의미 없는 copy/allocation
- hot path에서의 과도한 logging
- polling 주기 증가, blocking 호출 추가, 불필요한 lock 범위 확대
- 기존보다 더 비싼 알고리즘이나 데이터 흐름으로 바뀐 부분

원칙:

- 눈에 띄는 비효율이나 회귀 위험이 있을 때만 수정한다.
- 측정 없이 단정하기 어려운 경우에는 "수정"보다 "리스크 명시"를 우선한다.

### 4. 설계/구현 설명 점검

리뷰어가 "왜 이렇게 바뀌었는가"를 diff만 보고 추론해야 하는 상태를 남기면 안 된다.

설명이 명확히 부족하면 관련 문서나 PR 설명 초안을 직접 보강한다.
단, 작업자 의도 확인 없이 추측해서 쓸 수 없는 항목은 보강하지 말고 확인 필요 사항으로 남긴다.

반드시 확인할 항목:

- 이번 변경의 목적과 성공 기준이 문서 또는 PR 설명에 드러나는가
- 어떤 동작이 before/after로 달라지는지 설명되어 있는가
- 핵심 파일 또는 파일군별로 "왜 수정했는가"가 적혀 있는가
- 테스트, 로그, 스크린샷, 수동 검증 등 실제 검증 근거가 있는가
- known issue, 비대상 범위, 후속 작업이 숨겨져 있지 않은가

아래 경우에는 설명 보강이 필요하다.

- 여러 모듈 간 흐름이나 책임 분리가 바뀌는 경우
- config, launch wiring, topic/service/API/schema, 배포 절차가 바뀌는 경우
- 구현 자체는 짧지만 설계 판단 이유를 알아야 리뷰가 가능한 경우

PR 설명 또는 문서 품질 점검에는 `ai/agentic_workbench/instructions/pr_description_guide.md`를 기준으로 사용한다.

### 5. 검증 실행

가능한 범위에서 아래를 수행한다.

- 수정한 repo 또는 submodule에서 formatting 스크립트 실행 (예: `./script/fix-format.sh .`)
- 관련 테스트, 빌드, lint, 정적 검사 실행
- 자동 검증이 부족하면 최소한 핵심 시나리오 수동 검증 근거 정리

검증 규칙:

- 실행하지 못한 검증은 생략 이유를 남긴다.
- 실패한 검증이 있으면 숨기지 말고 원인과 영향 범위를 함께 보고한다.
- 포맷팅이나 테스트 통과 여부를 추측해서 적지 않는다.

### 6. 최종 보고

최종 응답에는 최소한 아래 내용을 포함한다.

- 실제로 정리한 항목
- 남겨둔 항목과 그 이유
- 문서/PR 설명에서 아직 작업자 확인이 필요한 부분
- 실행한 검증과 결과
- 지금 PR을 열어도 되는지, 아니면 선행 수정이 더 필요한지에 대한 판단

## 금지 사항

- diff와 무관한 코드 스타일보정이나 대규모 리팩터링
- 근거 없는 성능 개선 주장
- 설계 의도를 추측해서 문서나 PR 설명을 채우는 일
- 실패한 테스트, 미확인 리스크, 애매한 비대상을 보고에서 누락하는 일
- "일단 PR부터 올리고 보자" 식으로 검증/설명 부족 상태를 정상으로 취급하는 일
