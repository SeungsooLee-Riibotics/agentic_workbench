# PR Intake Gate: 설계 문서만으로 판단 가능한가 (MVP)

이 문서는 PR 리뷰어 측의 1차 intake gate 기준이다.
목표는 이 PR이 **설계 문서와 PR 요약만으로 판단 가능한지**, 아니면 **코드 리뷰가 추가로 필요한지**, 혹은 **문서 패키지 자체가 부족한지**를 먼저 가르는 것이다.

이 문서는 작성자가 자기 PR 설명을 준비하는 용도의 문서가 아니다. 작성자 측 준비는 `pr_author_prepare_guide.md`, `PR_GUIDE.md`, `pr_description_guide.md`, `refine_before_pr.md` 흐름으로 본다.

판정값은 아래 3개만 사용한다.

- `DOC_ONLY_REVIEW_POSSIBLE`
- `CODE_REVIEW_REQUIRED`
- `DOC_PACKAGE_INSUFFICIENT`

---

## 목적

- PR의 변경 의도, 범위, 설계 판단, 영향 범위, 검증 근거가 문서로 충분히 드러나는지 판단한다.
- 코드 품질 자체를 깊게 검토하는 것이 아니라, **설계 수준의 판단이 문서에서 끝날 수 있는지**를 본다.
- 리뷰어가 diff 전체를 먼저 뒤지지 않아도 될 상태인지 가른다.

---

## 언제 사용하는가

- PR 링크를 받고, 코드에 들어가기 전에 문서 패키지의 충분성을 먼저 판단하고 싶을 때.
- 변경 범위가 여러 파일에 걸쳐 있지만, 핵심 판단이 설계 문서와 PR 설명에 이미 담겨 있어야 한다고 기대할 때.
- 빠르게 "문서만 보면 되는 PR인가"를 가르고, 그렇지 않으면 코드 리뷰로 넘기고 싶을 때.

이 문서는 작성자용 PR 작성 가이드를 대체하지 않는다. 작성 품질 기준 자체는 `instructions/PR_GUIDE.md`, `instructions/pr_description_guide.md`를 참고하고, 이 문서는 **그 기준이 실제로 충족되었는지 리뷰어 입장에서 판정**하는 데 사용한다.

---

## 입력

- PR 링크
- PR 요약 / PR 본문
- changed files 목록
- PR에 포함된 문서
- PR 본문에서 링크한 문서
- 검증 근거(테스트, 로그, 수동 검증 메모, acceptance criteria 등)

필요 시 아래 성격의 변경이 있는지도 함께 본다.

- 로직 변경
- 인터페이스 / schema 변경
- config / deploy / ops 변경
- 문서 변경
- 테스트 변경

이 문서는 changed files **내용을 깊게 리뷰하지는 않지만**, 어떤 종류의 변경이 있는지는 판단 근거로 사용한다.

---

## 핵심 원칙

1. 이 가이드는 깊은 코드 품질 검토가 아니라 **문서 충분성 판정**을 위한 것이다.
2. 문서에 없는 작성자 의도를 추측해서 보완하지 않는다.
3. PR 요약과 문서는 diff의 재서술이 아니라 **왜 바꾸는지, 무엇이 달라지는지, 어디에 영향이 있는지**를 설명해야 한다.
4. 의미 있는 변경 파일 또는 파일군은, 어떤 문서에서 왜 설명되는지 추적 가능해야 한다.
5. config, API, schema, 배포, 운영 절차 영향은 문서상에서 드러나야 한다.
6. 검증 근거가 없으면 "문서만으로 판단 가능" 판정을 주지 않는다.
7. 불명확한 점이 있으면 `instructions/ask.md` 원칙에 따라 추정하지 말고 질문으로 되돌린다.

설계 문서의 충분성은 필요 시 `instructions/design_request_guide.md`의 관점으로 본다.
즉 목표, 성공 기준, 요구사항, 제약, 데이터/인터페이스, 검토 포인트가 빠져 있지 않은지 본다.

---

## 판정값

### 1. `DOC_ONLY_REVIEW_POSSIBLE`

아래가 모두 만족될 때만 사용한다.

- 변경 목적과 성공 기준이 PR 요약 또는 링크 문서에 명확하다.
- 변경 범위와 비대상 범위가 문서에 드러난다.
- 의미 있는 changed file 그룹마다 대응 문서 또는 PR 섹션이 있다.
- config / API / schema / deploy / ops 영향이 문서에서 추적 가능하다.
- 검증 근거가 문서에 남아 있다.
- 링크 문서가 최신이며 PR 요약과 모순되지 않는다.
- changed files 성격상, 핵심 판단이 코드 속에 숨어 있지 않다.

### 2. `CODE_REVIEW_REQUIRED`

문서는 어느 정도 갖춰져 있지만, 핵심 판단이 코드 확인 없이는 끝나지 않을 때 사용한다.

예시:

- 알고리즘 선택이나 상태 전이 판단이 중요하다.
- 예외 처리, 실패 복구, 동시성, 보안, 성능 tradeoff가 핵심이다.
- 마이그레이션 로직이나 rollout 안전성이 구현 세부에 강하게 의존한다.
- PR 설명은 충분하지만, correctness 판단은 실제 코드 흐름을 봐야 한다.

이 값은 "문서가 나쁘다"가 아니라, **문서만으로는 리뷰를 끝낼 수 없다**는 뜻이다.

### 3. `DOC_PACKAGE_INSUFFICIENT`

문서 패키지 자체가 부족해서 설계 판단도 시작하기 어려울 때 사용한다.

예시:

- 변경 목적이나 성공 기준이 없다.
- 범위와 비대상이 모호하다.
- 의미 있는 changed file 그룹이 어떤 문서와 연결되는지 알 수 없다.
- 영향 범위(config / API / schema / deploy / ops)가 문서에 없다.
- 검증 근거가 비어 있다.
- 링크 문서가 깨졌거나 오래되었거나 PR 내용과 모순된다.

---

## 판정 기준

아래 항목을 기준으로 판정한다.

### 1. 변경 목적의 명확성

- 이 PR이 해결하려는 문제가 무엇인지 드러나는가?
- 안 바꾸면 남는 문제가 무엇인지 설명되는가?
- 성공 기준이 보이는가?

### 2. 범위 / 비대상 명확성

- 이번 PR이 어디까지 책임지는지 드러나는가?
- 의도적으로 제외한 범위가 적혀 있는가?
- 후속 작업이 필요한지 드러나는가?

### 3. changed file - 문서 매핑

- 리뷰 의미가 있는 파일 또는 파일군이 어떤 문서 또는 PR 섹션에 대응되는가?
- "무엇이 바뀌었는가"보다 "왜 이 파일군이 바뀌어야 했는가"가 설명되는가?

### 4. 영향 추적

아래 중 하나라도 바뀌면 문서에서 추적 가능해야 한다.

- config 기본값
- API / topic / service / schema / interface
- deploy 절차
- 운영 절차
- 사용 방법

### 5. 검증 근거

- 테스트, 로그, 수동 검증, acceptance criteria 중 실제 근거가 있는가?
- "문제 없음", "테스트 완료" 같은 근거 없는 문구에 의존하지 않는가?

### 6. 링크 문서의 일관성 / 최신성

- 링크된 설계 문서가 실제로 열리는가?
- 현재 PR의 범위와 버전이 맞는가?
- PR 요약과 링크 문서가 서로 모순되지 않는가?

### 7. 코드 확인 필요성

문서가 좋아 보여도 아래 성격이면 `CODE_REVIEW_REQUIRED` 쪽으로 기운다.

- 핵심 판단이 로직 세부에 숨어 있는 경우
- correctness가 구현 흐름에 크게 의존하는 경우
- 설계 문서보다 코드에서 더 많은 판단이 드러나는 경우

---

## 작업 순서

1. **PR 요약과 링크 문서를 먼저 읽는다.**
   - 변경 목적, 성공 기준, 범위, 비대상, 검증 근거가 있는지 본다.

2. **changed files를 의미 있는 그룹으로 본다.**
   - 로직 / 인터페이스 / config / deploy / docs / tests 관점으로 나눈다.

3. **각 파일군이 어느 문서에서 설명되는지 매핑한다.**
   - 설명이 없는 파일군이 있으면 바로 표시한다.

4. **영향 범위를 추적한다.**
   - config, API, schema, deploy, ops 영향이 문서에 있는지 확인한다.

5. **검증 근거를 확인한다.**
   - 테스트, 로그, 수동 검증, acceptance criteria 중 실제 근거가 있는지 본다.

6. **링크 문서의 최신성과 일관성을 확인한다.**
   - 링크가 열리는지, 현재 PR과 맞는 문서인지, 서로 충돌하지 않는지 본다.

7. **최종 판정을 내린다.**
   - 문서만으로 설계 판단이 끝나면 `DOC_ONLY_REVIEW_POSSIBLE`
   - 문서는 괜찮지만 코드 확인이 필요하면 `CODE_REVIEW_REQUIRED`
   - 문서 패키지가 부족하면 `DOC_PACKAGE_INSUFFICIENT`

---

## 작성자에게 되돌릴 질문

아래 질문은 `DOC_PACKAGE_INSUFFICIENT` 또는 경계 상황에서 사용한다.

- 이 PR의 변경 목적과 성공 기준을 1~3줄로 더 명확히 적어줄 수 있는가?
- 이번 PR의 비대상 범위와 후속 작업은 무엇인가?
- 이 changed file 그룹은 어떤 설계 문서 또는 PR 섹션에서 설명되는가?
- config / API / schema / deploy / ops 영향이 있다면, 관련 문서 링크를 추가할 수 있는가?
- 현재 링크된 문서 중 어떤 것이 최신 기준 문서인가?
- 검증 근거로 사용한 테스트, 로그, 수동 검증 시나리오를 더 구체적으로 남길 수 있는가?
- 문서로는 충분해 보이지만 코드 확인이 필요한 부분이 있다면, 어디가 핵심 리뷰 포인트인지 지정할 수 있는가?

---

## 최종 출력 형식

최종 결과는 최소한 아래를 포함한다.

- `Verdict`: `DOC_ONLY_REVIEW_POSSIBLE` / `CODE_REVIEW_REQUIRED` / `DOC_PACKAGE_INSUFFICIENT`
- `Why`: 이렇게 판단한 핵심 이유 2~5개
- `Missing or weak points`: 비어 있거나 약한 문서 근거
- `Questions back to author`: 작성자에게 되돌릴 질문
- `Recommended next step`: 문서 보강 요청 / 코드 리뷰 진행 / 문서 중심 리뷰 진행

---

## 금지 사항

- 이 가이드를 전체 코드 품질 리뷰로 확장하지 않는다.
- 문서에 없는 작성자 의도를 추정해서 채우지 않는다.
- 링크 문서가 불명확한데도 "문서만 보면 충분하다"고 성급히 결론내리지 않는다.
- 문서 패키지가 부족한 상태를 `CODE_REVIEW_REQUIRED`로 뭉개서 넘기지 않는다.
- 리뷰어가 다시 전체 diff를 뒤져야만 이해되는 상태를 정상으로 취급하지 않는다.
