# 내 PR 준비 가이드 (작성자용)

이 문서는 **내가 작성자일 때**, 브랜치 작업을 PR로 올리기 전에 무엇을 정리하고 어떤 instruction을 순서대로 써야 하는지 안내하는 entrypoint다.

즉, 이 문서는 **PR이 열리기 전(pre-open) author flow 전용**이다. PR이 이미 열렸고 reviewer 관점 intake가 필요하면 `pr_review_intake_gate.md`를, 열린 PR의 코멘트/자동 리뷰 피드백을 처리해야 하면 `ai_pr_review_apply.md`를 사용한다.

핵심은 단순하다.

- 이 가이드는 **내 PR을 준비하는 흐름**이다.
- 다른 사람 PR을 리뷰하는 흐름과 섞지 않는다.
- reviewer 입장에서 충분성을 판정하는 문서는 별도로 본다.

---

## 이 문서를 언제 쓰는가

아래 요청이면 이 문서를 먼저 탄다.

- "내 PR 올리기 전에 한 번 정리해줘"
- "이 브랜치 기준으로 PR 열 준비 됐는지 봐줘"
- "내 PR 설명 초안 작성해줘"
- "리뷰어가 이해하기 쉽게 내 변경을 구조화해줘"

즉, **PR이 아직 열리기 전이거나**, 열기 직전 작성자 입장에서 diff / 설명 / 검증 근거를 정리하는 상황이다.

---

## 이 문서를 쓰지 않는 경우

아래는 다른 흐름이다.

### 1. 다른 사람 PR을 리뷰하는 경우

- `pr_review_intake_gate.md`

이 문서는 reviewer 입장에서 문서만으로 판단 가능한지, 코드 리뷰가 필요한지, 문서 패키지가 부족한지 먼저 가르는 문서다.

### 2. 이미 열린 PR에서 리뷰 코멘트/자동 리뷰 피드백을 처리하는 경우

- `ai_pr_review_apply.md`

이 문서는 pre-PR 준비가 아니라 **post-PR feedback triage** 흐름이다. CodeRabbit 코멘트나 PR 피드백을 적용/보류/스킵할 때 사용한다.

---

## 작성자용 기본 흐름

### 1. 애매하면 먼저 질문

- `ask.md`

요구사항, 범위, 목적이 애매하면 구현/정리보다 먼저 질문을 정리한다.

### 2. 설계 요청이 먼저 필요한지 판단

- `design_request_guide.md`

구현보다 설계 정리가 먼저 필요한 상태면 이 문서로 요청 구조를 만든다.

### 3. PR 직전 diff와 검증 근거 정리

- `refine_before_pr.md`

이 단계에서 불필요한 변경, dead code, 임시 코드, 빠진 검증, 숨겨진 리스크를 정리한다.

### 4. PR 본문 구조 잡기

- `PR_GUIDE.md`

PR 제목, 개요, 변경 사항, 영향 범위, 검증/테스트, 체크리스트를 어떻게 배치할지 잡는다.

### 5. PR 설명 품질 높이기

- `pr_description_guide.md`

리뷰어가 diff를 보기 전에 변경 의도, 영향 범위, 검증 근거를 이해할 수 있게 설명 품질을 끌어올린다.

---

## 작성자 입장에서 최종적으로 남겨야 하는 것

PR을 열기 전, 최소한 아래 5가지는 남아 있어야 한다.

1. **왜 바꾸는가**
2. **이번 PR 범위와 비대상**
3. **핵심 파일/파일군을 왜 바꿨는가**
4. **어떻게 검증했는가**
5. **남는 리스크와 후속 작업**

---

## 추천 요청 예시

- "내 브랜치 기준으로 PR 올리기 전에 정리해줘. 작성자용 흐름으로 해줘."
- "내 PR 설명 초안 작성해줘. reviewer가 diff 보기 전에 이해할 수 있게."
- "작성자 입장에서 지금 PR 준비 상태 점검해줘. refine_before_pr 기준으로."
- "내 변경 범위를 reviewer-friendly 하게 구조화해줘. PR_GUIDE + pr_description_guide 기준으로."

---

## reviewer 관점 self-check를 하고 싶을 때

작성자라도 마지막에 reviewer 관점 self-check를 해볼 수는 있다.
다만 그때 쓰는 문서는 여전히 reviewer 문서다.

- self-check 전까지는 이 문서의 흐름을 따른다.
- 마지막에 "문서 패키지가 reviewer 기준으로 충분한가"를 보고 싶으면 `pr_review_intake_gate.md`를 별도로 사용한다.

즉:

- **준비는 작성자 가이드로 하고**
- **최종 충분성 판정은 reviewer gate로 본다**

이 둘을 한 문서에서 섞지 않는 것이 핵심이다.
