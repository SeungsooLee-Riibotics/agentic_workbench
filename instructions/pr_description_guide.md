# PR Description Guide (작성자용)

이 문서는 `.github/PULL_REQUEST_TEMPLATE.md`를 채울 때 따라야 하는 **작성자용 작성 기준**이다.
목표는 리뷰어가 코드를 보기 전에 변경 의도와 영향 범위를 예상할 수 있게 만들고, 가능하면 PR 설명만으로도 핵심 변경을 이해하게 하는 것이다.

리뷰어 입장에서 문서만으로 판단 가능한지 가르는 문서는 별도로 `pr_review_intake_gate.md`를 사용한다.

## 핵심 원칙

- PR 설명은 diff의 재서술이 아니라 변경 의도와 영향 범위의 요약이어야 한다.
- 코드에서 확인 가능한 사실과 작업자의 의도는 구분해서 작성한다.
- 의도가 조금이라도 애매하면 추측해서 작성하지 말고 브랜치 작업자와 먼저 논의한다.
- 이번 PR에 포함하지 않은 범위도 명시한다. 그래야 리뷰어가 빠진 작업과 의도적 제외를 구분할 수 있다.
- 리뷰어가 "어디부터 읽어야 하는지"를 알 수 있도록 파일 또는 파일군 단위로 수정 이유를 적는다.

## 작업자와 반드시 논의해야 하는 경우

아래 항목 중 하나라도 불명확하면 PR 설명 작성 전에 브랜치 작업자와 확인한다.

- 이 수정의 원래 목적과 성공 기준
- 이번 PR에서 의도적으로 제외한 범위
- 여러 구현안 중 현재 방식을 선택한 이유
- 임시 우회인지, 최종 해법인지
- 설정값, 인터페이스, 배포 절차, 운영 절차에 미치는 영향
- known issue 또는 후속 PR이 필요한지 여부

확인 없이 추정 작성하면 안 되는 항목:

- "왜 이렇게 수정했는가"
- "왜 다른 방식이 아니라 이 방식인가"
- "이번 PR에서 어디까지 책임지는가"

## 필수 항목

모든 PR 설명에는 아래 내용이 포함되어야 한다.

### 1. 왜 바꾸는가

- 해결하려는 문제를 1~3줄로 적는다.
- 안 바꾸면 어떤 문제가 남는지도 적는다.

### 2. 무엇이 달라지는가

- 사용자, 운영자, 시스템 관점에서 before/after를 적는다.
- 구현 세부보다 결과와 영향 중심으로 적는다.

### 3. 어디를 왜 바꿨는가

- 리뷰 의미가 있는 파일 또는 파일군 단위로 정리한다.
- 각 항목은 최소한 `무엇이 바뀌었는가`보다 `왜 이 파일이 수정되어야 했는가`를 설명해야 한다.
- 사소한 기계적 변경은 묶어서 적는다.

권장 형식:

```md
| File / Group | Why changed | Key point for reviewer |
| --- | --- | --- |
| `src/...` | 수정 이유 | 우선 확인할 포인트 |
```

### 4. 어떻게 검증했는가

- 실행한 테스트, 수동 검증 시나리오, 로그, 스크린샷, 측정값 중 실제 근거를 적는다.
- "테스트 완료" 같은 근거 없는 문구는 금지한다.

### 5. 남는 리스크와 비대상

- known issue, 롤아웃 주의점, 후속 작업 필요 사항을 적는다.
- 이번 PR에서 일부러 하지 않은 일도 적는다.

## 조건부 필수 항목

해당되는 경우에는 반드시 포함한다.

### 1. 도식화

아래 상황이면 간단한 다이어그램, 흐름도, 표, 시퀀스 요약 중 하나를 넣는다.

- 여러 모듈 간 데이터 흐름이 바뀌는 경우
- 상태 전이, 제어 흐름, 토픽/서비스/API 연결이 바뀌는 경우
- 단순 코드 수정이 아니라 구조 이해가 중요한 경우

### 2. 설정/마이그레이션/운영 영향

아래 중 하나라도 바뀌면 반드시 적는다.

- config 기본값
- launch wiring
- topic / service / API / message schema
- 배포 순서
- 운영 절차 또는 사용 방법

### 3. 리뷰 집중 포인트

작성자가 특히 검토받고 싶은 부분이나 확신이 낮은 부분이 있으면 반드시 적는다.

## 파일별 설명 규칙

- 모든 파일을 raw diff처럼 나열하지 않는다.
- 리뷰 의미가 있는 파일 또는 파일군만 정리한다.
- 포맷팅만 한 파일, generated file, rename only 변경은 별도 묶음으로 처리한다.
- 테스트 파일은 "무엇을 검증하려고 수정했는지"까지 적는다.
- 설정 파일은 "어떤 동작 변화와 연결되는지"를 적는다.

좋은 예:

- `src/path_planner.cpp`: 장애물 감지 후 재계산이 늦게 일어나던 문제를 해결하기 위해 재계산 트리거 조건을 수정
- `test/path_planner_test.cpp`: 기존 버그를 재현하고 회귀를 막기 위한 케이스 추가

나쁜 예:

- `src/path_planner.cpp`: 코드 수정
- `test/path_planner_test.cpp`: 테스트 수정

## 템플릿 매핑

`.github/PULL_REQUEST_TEMPLATE.md`의 각 섹션은 아래 기준으로 채운다.

### PR Overview

- 왜 바꾸는가
- 최종적으로 무엇이 달라지는가
- 이번 PR의 비대상

### PR Detail

- 파일 또는 파일군별 수정 이유
- 필요하면 before/after 요약
- 필요하면 도식화

### Related Issue (Option)

- 관련 이슈, 장애 보고, 요구사항 문서 링크

### Issues of PR

- 남는 리스크
- known issue
- 후속 작업 필요 사항

### Documentation

- 관련 문서 링크
- 테스트 로그, 스크린샷, 검증 근거
- 설정 변경이나 운영 변경 문서가 있다면 함께 링크

### Request for reviewer (Option)

- 집중 리뷰 요청 지점
- 작성자가 확신이 낮은 부분
- 선택한 구현 방향이 적절한지 확인받고 싶은 포인트

### ETC (Option)

- 위 섹션에 넣기 애매하지만 남겨둘 필요가 있는 메모
- 내용이 없으면 비워둔다

## 금지 사항

- diff를 항목별로 그대로 풀어 쓴 설명
- 작업자 의도를 추측해서 단정적으로 작성한 설명
- 근거 없는 "문제 없음", "테스트 완료", "영향 없음"
- 비대상과 known issue를 숨기는 서술
- 리뷰어가 다시 diff 전체를 뒤져야만 이해되는 모호한 설명

## 최소 작성 예시

```md
## PR Overview
- 장애물 감지 직후 경로 재계산이 지연되던 문제를 수정
- 감지 후 즉시 재계산이 수행되며, idle 상태의 기존 동작은 유지
- 지도 갱신 주기 최적화는 이번 PR 범위에 포함하지 않음

## PR Detail
| File / Group | Why changed | Key point for reviewer |
| --- | --- | --- |
| `src/path_planner.cpp` | 재계산 트리거 조건 누락 수정 | 기존 idle flow 회귀 여부 확인 필요 |
| `include/path_planner.hpp` | 상태/인터페이스 변경 반영 | 외부 호출부 영향 확인 |
| `test/path_planner_test.cpp` | 버그 재현 및 회귀 방지 케이스 추가 | corner case 포함 여부 확인 |
| `launch/nav.launch.py`, `config/nav.yaml` | 새 파라미터 연결 및 기본값 반영 | 배포 기본값 영향 확인 |

## Issues of PR
- 장애물 센서 오탐이 많은 환경에서는 재계산 빈도가 높아질 수 있음
- 파라미터 튜닝은 후속 PR에서 진행 예정

## Documentation
- 수동 검증: 장애물 삽입 후 10회 반복 테스트
- 단위 테스트: `path_planner_test` 추가 및 통과

## Request for reviewer
- 재계산 트리거 조건이 기존 idle 복귀 흐름에 미치는 영향 중점 확인 요청
```
